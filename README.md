# murder-loop-ai

## v1.2 更新摘要

本版本重点完成了 AI Agent 架构收口、World Info Lite、结构化上下文与凶手信息边界修复，目标是让开放输入下的叙事更稳定、凶手不再全知、各 Agent 能按职责读取上下文。

### 架构与 Agent Contract

- 统一到 harness 架构，收口旧流程中的重复路径。
- 引入 Agent Contract 与 Agent Trace，记录每个 Agent 的输入、输出、校验结果、fallback 状态和耗时。
- Agent Trace 现在会记录每回合命中的 World Info 摘要，只保存 `id / title / source / priority`，不把卡片正文暴露到普通 UI。

### 结构化记忆与 ContextBuilder

- 完成结构化循环记忆基础：短期记忆、本轮记忆、跨轮记忆、角色记忆。
- 新增 ContextBuilder，统一决定 Parser / Killer / Narrator / Director 每回合能看到什么。
- Killer 只接收可观察事件、投影后的可见状态、凶手记忆和允许的 World Info，不再默认读取完整世界状态。
- Director 接入 trace、叙事、规则结果和 World Info，用于一致性检查。

### World Info Lite

- 新增轻量版 World Info 卡片系统，覆盖规则卡、关键物品卡、线索卡、NPC 卡和故事核心卡。
- 已按人工校验后的“草稿描述”回填运行时卡片。
- 关键规则包括：
  - 凶手信息边界
  - 门窗防御互不替代
  - 警察身份核验
  - 叙事不能改规则
  - World Info 不是规则裁判
  - 手机活动可见性
  - 禁止凭空新增物品和路线
  - 叙事不能替玩家读心
- 林越已统一设定为主角的前男友，是外部求救和证据备份角色，不是凶手。

### Killer / Narrator Prompt 接入

- Killer、Action Narrator、Ambient Narrator 的 server prompt 已接入 World Info Lite。
- prompt 明确说明 World Info 只是设定上下文，不是规则裁判。
- Narrator 不能根据 World Info 自行新增死亡、逮捕、逃脱、线索或状态变化。
- Killer 使用 World Info 时必须受 `killerContext.visibleState` 和 `killerContext.observableEvents` 限制。

### 凶手信息泄露修复

- 修复“玩家检查纸板箱看到药片后，门外人直接短信说别碰药片”的信息泄露风险。
- Killer AI prompt payload 现在只传 `killerContext`，不再传完整 `plan` 和完整 `playerResult`。
- `killerContext.planSummary` 不再使用玩家原始动作摘要，只从 `visibility === 'killer'` 的可观察事件生成。
- `updateKillerKnowledgeFromState()` 不再因为房间状态里 `package.opened = true` 就让凶手确定知道玩家打开了包裹；只有传入 killer 可见事件时才升级相关知识。
- 已加入回归测试，确保 Killer payload 中不会出现 `药片`、`药板`、`package contents`、玩家原始动作或完整规则结果文本。

## 1. 项目背景

很多 AI 剧情产品采用“玩家输入 → 单个 AI 续写剧情”的模式。这种方式实现简单，但容易出现几个问题：

- AI 胡编事实，破坏前后逻辑；
- AI 过度顺从玩家，缺少真正对抗；
- 一个 AI 同时扮演作者、裁判、凶手和 NPC，容易人格混乱；
- AI 知道所有信息，角色经常开上帝视角；
- 没有规则系统约束，玩家死亡或通关缺乏可信原因。

本项目尝试把 AI 从“万能作者”拆分为多个受约束的协作角色：

```txt
玩家自然语言输入
→ 行动解析 AI
→ 本地规则裁判系统
→ 凶手 AI 在有限信息下反制
→ 规则系统校验凶手策略
→ 叙事 AI 小说化输出
→ 证据、记忆、评分系统记录结果
```

核心原则是：

```txt
玩家和 AI 共同创作故事，
但规则系统拥有最终解释权。
```

## 2. 游戏内容概述

### 一句话定义

你不是在阅读悬疑小说，而是在和 AI 一起写一部会杀死你的小说。

### 核心设定

故事发生在青荷公寓 503 室。主角沈知夏刚搬进这间出租屋，却误收了一个装有毒品的包裹。这个包裹原本属于房东陈怀民控制的地下毒品转运链，一旦被发现并交给警方，陈怀民就会坐牢，甚至牵出背后的整条链。

第一轮中，沈知夏没有意识到危险，在 23:47 被杀。死亡后，她带着模糊的死亡碎片回到 23:00，必须利用每一轮获得的记忆，逐步理解包裹、房东、林越、假警察和 23:47 的意义。

### 核心人物

- **沈知夏**：玩家扮演的主角，刚搬入青荷公寓 503。
- **陈怀民**：青荷公寓房东，真实身份是地下毒品转运链的关键人物，也是凶手。
- **林越**：沈知夏的前男友，不是凶手，但可能成为救援变量、误导源或风险点。
- **真警察 / 假警察**：报警不是自动通关，玩家需要核实身份并保全证据。

### 玩家目标

活下来只是最低目标。更好的结局需要玩家：

- 保住自己；
- 保留包裹、照片、录音等证据；
- 让林越和无辜 NPC 尽量安全；
- 识别假警察与陈怀民的谎言；
- 理解 23:47 与毒品包裹转运的真相；
- 让警方获得可信证据，而不是被嫁祸或误导。

## 2.5 故事线总览

这一节是给后续扩写剧情、优化 prompt、修复 AI 跑偏时使用的故事总表。所有 AI 叙事、凶手策略和规则系统都应该服从这里的事实边界。

### 主线一句话

刚搬进青荷公寓 503 的沈知夏误收了一个装有毒品的包裹。包裹原本属于房东陈怀民控制的地下毒品转运链。陈怀民发现包裹落到沈知夏手里后，害怕毒品被发现、照片被外传、自己坐牢并牵出整条链，于是在第一轮 23:47 杀死沈知夏灭口。死亡后，沈知夏不断回到 23:00，必须在有限时间内确认毒品包裹的真相、保存证据、识别陈怀民与假警察的欺骗，并把可信证据送出房间。

### 小说主故事线

#### 第一幕：错误包裹

沈知夏搬进青荷公寓 503 的第一晚，房间还没收拾完，快递和行李堆在门口。她太累，顺手把一个标着 `5-03` / `503` 的包裹拿进屋，以为是自己的快递或搬家遗落物。

包裹表面看起来像普通旧书和药盒，但里面夹着密封袋、伪装药片和毒品。沈知夏没有立刻意识到这是犯罪证据，只觉得不对劲，可能拍了照片，可能发给林越吐槽，也可能只是放在桌上准备明天处理。

这一幕的核心不是“恐怖”，而是现实里的错位：一个普通租客因为拿错快递，突然握住了足以让房东坐牢的证据。

#### 第二幕：房东发现

陈怀民表面是青荷公寓房东，真实身份是地下毒品转运链里的关键节点。他利用老旧公寓的空房、混乱门牌、快递堆放习惯和备用钥匙，把部分房间当作临时收货点。

那个装有毒品的包裹本来不该进入 503。它一旦被沈知夏发现并报警，陈怀民面对的不是“丢了一件货”，而是毒品、转运链、房东身份和多个空房收货点全部暴露。他会坐牢，也可能被上游追责。

所以陈怀民必须确认三件事：

1. 沈知夏有没有拆开包裹；
2. 她有没有看见里面是毒品；
3. 她有没有拍照、发给别人或报警。

#### 第三幕：第一次死亡

第一轮，沈知夏没有警觉。她太累，没有认真处理包裹，也没有意识到房东已经盯上了她。

23:47，陈怀民利用备用钥匙或已经掌握的公寓权限进入 503，把沈知夏杀死。她死前只记得几个碎片：门锁轻响，手机亮了一下，旧书和药盒混在潮湿纸箱里的味道，一个戴手套的人靠近床边，低声问：“东西呢？”

死亡后，沈知夏回到 23:00。

#### 第四幕：循环调查

第二轮开始，沈知夏知道自己会死，但不知道为什么。她可以检查门锁、猫眼、窗户、床底、衣柜、卫生间，也可以重新拆包裹、拍照、录音、备份、藏匿、联系林越或报警。

每个选择都会改变陈怀民的判断。如果她回复陌生号码“有啊，怎么了”，陈怀民就会确认她看见过包裹；如果她沉默，陈怀民会继续试探；如果她拍照外传，陈怀民会开始考虑夺回证据、误导林越或伪装警察；如果她过早质问房东，陈怀民会意识到她已经警觉。

这一幕的核心悬疑是：沈知夏从“我为什么会死”逐渐推进到“包裹里的毒品会让陈怀民坐牢，所以他必须让我闭嘴”。

#### 第五幕：外部证据链

林越不是凶手。他是沈知夏能否把证据送出房间的关键变量。沈知夏可以把毒品包裹照片发给林越，让他在楼下报警、备份照片、拍摄公寓出入口，而不是贸然上楼。

警察也不是自动通关按钮。陈怀民可能利用沈知夏等待救援的心理，让假警察提前出现，骗她开门。真正安全的做法是官方回拨、核实警号、要求站到猫眼可见位置、让林越在楼下确认。

#### 第六幕：23:47 压力点

23:47 是毒品包裹原本应该完成交接、回收或确认异常的时间点。到了这个时间，如果沈知夏还没有把证据传出去，也没有有效防御门窗、核实警方、保护包裹，陈怀民会升级行动：备用钥匙、假警察、断电、窗户路线、嫁祸或直接灭口。

### 核心真相

- 包裹原本不属于沈知夏。
- 包裹里有毒品，被旧书、药盒、密封袋等伪装物掩盖。
- 陈怀民利用青荷公寓的空房、混乱门牌、快递堆放和备用钥匙做毒品转运。
- 陈怀民杀沈知夏的直接动机是：害怕毒品被发现后自己坐牢，并牵出整条毒品转运链。
- 陈怀民要确认包裹是否在沈知夏手中、是否被拆、是否被拍照、是否发给别人。
- 第一轮死亡的“东西呢？”指的是装有毒品的包裹。
- 23:47 是毒品包裹交接、回收或灭证的压力节点。

### 主要角色线

#### 沈知夏

玩家主角。初始状态疲惫、受伤、信息不足。她的成长来自循环记忆：从不知道为何被杀，到逐步学会不轻易开门、保留证据、核实身份、利用外部联系。

#### 陈怀民

房东、凶手、地下毒品转运链关键人物。他熟悉公寓结构，掌握部分备用钥匙，知道快递与空房机制。他的目标优先级是：确认毒品包裹、拿回包裹、确认照片/备份、删除或污染证据、阻断外部联系、避免坐牢，必要时杀人或嫁祸。

#### 林越

前男友，外部求救链。不是凶手，但可以作为误导源和压力点。他能帮忙备份照片、报警、在楼下确认情况。玩家如果处理不好，也可能让他被引上楼或被卷入危险。

#### 真警察 / 假警察

真警察需要可信信息和证据才能有效介入。假警察用于打破“报警等于通关”的简单逻辑。玩家必须通过官方回拨、警号、猫眼、林越楼下确认等方式核实身份。

### 线索线

- `wrong_package`：包裹标记模糊，说明可能不是寄给沈知夏。
- `package_photo`：毒品包裹照片，是证据外传和高分结局的起点。
- `linyue_has_photo`：林越收到毒品包裹照片，外部备份成立，但林越风险上升。
- `door_scratch`：门锁划痕，说明有人尝试进入。
- `recording_pressure`：录音记录门外停顿和试探。
- `police_verified`：官方核实出警，可削弱假警察路线。
- `chen_probe`：陈怀民反复试探包裹和快递，但不敢直接说毒品。

### 死亡与失败路线

- 默认 23:47 死亡：没有保存证据、没有有效防御、没有可信外援。
- 假警察死亡：玩家报警后没有核实身份，主动开门。
- 备用钥匙入室死亡：门没有反锁、门链、堵门或录像威慑。
- 窗户路线死亡：门被堵住但窗户未锁、窗帘未处理。
- 屋内藏匿路线死亡：玩家离开房间或开门后，没有检查衣柜、床底、卫生间等位置。
- 嫁祸失败：玩家活着，但证据不足、毒品包裹被移动污染，陈怀民仍能脱身或反咬。

### 生还与高分路线

- 低分逃脱：玩家离开房间或撑过危险，但证据不足，真相没有闭合。
- 中分报警生还：玩家保存照片/录音，核实真警察，门窗防御合理，等到外部介入。
- 高分反制：玩家保住毒品包裹和照片，套出陈怀民矛盾，识别假警察，保护林越，形成可信证据链。
- 完美真相：毒品实物、照片、录音、门锁痕迹、陈怀民话术矛盾和真警察核验全部闭合，陈怀民害怕坐牢而灭口的动机被锁死，玩家和关键 NPC 尽量安全。

### AI 事实边界

- 叙事 AI 不能新增关键事实，不能让角色突然进场。
- 凶手 AI 只能根据 `killerKnowledge` 和可见状态行动。
- 玩家没有执行的动作不能被叙事补成事实。
- 玩家回复消息时，只能承接对话，不能自动追加敲门、脚步、断电等新压力，除非规则事件明确发生。
- 行动回应只写玩家动作落地结果；环境播报只写外部环境和暗线反馈。
- 任何死亡、生还、证据变化、NPC 状态变化都必须由规则系统决定。

## 3. 核心玩法

玩家主要通过自然语言输入行动，而不是点击固定选项。

示例：

```txt
我不直接拆包裹，先拍一张照片发给林越，然后把包裹恢复原样，再用椅子抵住门。
```

系统会将输入拆分为结构化行动，例如：保存证据、联系林越、加固门、推进时间、增加噪音风险等。随后规则系统判断行动是否可行，并更新世界状态。

### 单回合流程

```txt
玩家输入行动
→ AI 解析行动
→ 规则系统执行玩家行动
→ 凶手 AI 根据已知信息选择策略
→ 规则系统校验凶手行动
→ 叙事 AI 输出小说化反馈
→ 更新时间、威胁、线索、NPC 和结局状态
```

### 凶手对抗原则

凶手 AI 不能读取完整游戏状态，只能看到“凶手可能知道的信息”。例如，玩家如果把包裹藏进卫生间水箱，但没有发出明显声音、没有暴露位置，凶手不能凭空知道证据位置。

凶手可能采取的策略包括：

- 短信试探；
- 轻敲门；
- 假装房东维修；
- 假警察施压；
- 备用钥匙开门；
- 断电；
- 窗户路线；
- 引诱林越上楼；
- 退避、嫁祸或转移证据。

### 前端

- React
- TypeScript
- Vite
- Zustand / 本地状态管理方向
- Framer Motion / motion 动效
- 文本剧情面板
- 玩家输入框
- 右侧线索与状态栏
- 开场与结局过场动画

### 后端

- Node.js
- Fastify
- TypeScript
- OpenAI-compatible SDK 调用方式
- 多 provider / 多 role AI 配置
- Zod schema 校验 AI 输出
- 本地 fallback 保证无 API key 时仍能跑通核心闭环

### 核心包

- `packages/shared`：定义 GameState、ActionPlan、KillerStrategy、Narration、ScoreResult 等核心类型。
- `packages/ai-contracts`：约束 AI 输出结构，防止模型返回不可用内容。
- `packages/content`：维护故事圣经、房间信息、线索和 NPC 内容。
- `packages/game-core`：实现行动执行、凶手策略应用、回溯、叙事上下文、评分等规则逻辑。

## 6. AI 配置说明

项目把 AI 配置分成两层：

1. **Provider 级配置**：配置某个模型服务的 key、base URL 和默认模型。
2. **Role 级配置**：配置某个游戏角色或功能使用哪个 provider。

### Provider 示例

```env
OPENAI_API_KEY=
OPENAI_BASE_URL=
OPENAI_MODEL=gpt-4o-mini

DEEPSEEK_API_KEY=
DEEPSEEK_BASE_URL=https://api.deepseek.com/v1
DEEPSEEK_MODEL=deepseek-chat

DEEPSEEK_KILLER_API_KEY=
DEEPSEEK_KILLER_BASE_URL=https://api.deepseek.com/v1
DEEPSEEK_KILLER_MODEL=deepseek-v4pro

DEEPSEEK_NPC_API_KEY=
DEEPSEEK_NPC_BASE_URL=https://api.deepseek.com/v1
DEEPSEEK_NPC_MODEL=deepseek-v4pro

DEEPSEEK_RECAP_API_KEY=
DEEPSEEK_RECAP_BASE_URL=https://api.deepseek.com/v1
DEEPSEEK_RECAP_MODEL=deepseek-v4pro

DUCKINGMIND_API_KEY=
DUCKINGMIND_BASE_URL=https://api.duckingmind.com/v1
DUCKINGMIND_MODEL=gpt-4o-mini
```

### Role 示例

```env
AI_PARSE_PROVIDER=deepseek
AI_KILLER_PROVIDER=deepseek_killer
AI_NARRATOR_PROVIDER=duckingmind
AI_NPC_PROVIDER=deepseek_npc
AI_RECAP_PROVIDER=deepseek_recap

AI_PARSE_MODEL=
AI_KILLER_MODEL=deepseek-v4pro
AI_NARRATOR_MODEL=
AI_NPC_MODEL=
AI_RECAP_MODEL=
```

说明：即使没有配置 API key，项目也会使用本地 fallback 跑通核心游戏循环。

## 8. 当前开发进度评估

### 已完成阶段

#### Phase 0：设计确认

基本完成。已有完整软件设计文档、MVP 清单、故事设定和核心玩法定义。

#### Phase 1：项目初始化

基本完成。Monorepo、前端、服务端、共享类型、AI contracts、game-core 都已经建立。

#### Phase 2：核心文字循环

已完成原型闭环。玩家可以输入行动，服务端执行解析、规则裁判、凶手策略和叙事输出，前端显示结果。

### 进行中阶段

#### Phase 3：凶手对抗系统

已经具备基础版本：凶手知识边界、fallback 策略、AI 策略接口、假警察/备用钥匙/窗户路线等核心路线已存在。新增 `message_reply` 路径后，玩家回复消息时会先承接对话，不再直接跳到新的环境压力。但凶手长期规划、动态欺骗、多轮记忆利用和更复杂的嫁祸逻辑仍需要增强。

#### Phase 3.5：多 AI 协调与导演评分

已进入实现阶段。当前采用轻量“共享回合黑板 + 结构化事件 + 守卫规则 + 导演评分器”的方案，而不是直接套完整多 Agent 框架。行动解析、凶手策略、叙事和导演评分会共享回合事实；对于回复消息等高风险漂移场景，系统会绕过自由叙事，使用确定性叙事承接事实。

#### Phase 4：证据与评分

已有基础评分函数和线索系统，但证据链仍偏简化。当前更多是 MVP 级别的“线索 ID + 状态变化”，还未形成完整的证据推理、证据污染、证据提交和警方可信度系统。

### 尚未充分展开阶段

#### Phase 5：视觉与氛围

已有前端暗色悬疑 UI、开场/结局过场和基础动效，但尚未完成规划中的户型图、关键分镜、音效、出租屋主视觉和证据可视化。

## 9. 当前缺陷与限制

### 玩法层面

- 行动解析仍依赖 schema 和 fallback，复杂中文长指令可能解析不完整。
- 玩家确认系统还不完整，当前前端主要是直接提交并执行。
- 玩家自由度很高，但规则覆盖面还有限，很多细节行动会退化为默认处理。
- 23:47 后的升级阶段尚未充分展开。
- 多轮回溯记忆机制还没有完全产品化。
- 部分结局字段已经定义，但实际触发路径还不够丰富。

### 凶手 AI 层面

- 凶手策略已有有限信息原则，但长期计划能力仍偏弱。
- 凶手对玩家行为的识别主要依赖规则状态，缺少更细颗粒度的观察、误判和推理过程。
- 嫁祸、撤离、转移证据等高阶策略还需要扩展。
- 当前凶手压力更像“单步策略选择”，还不是完整的持续对抗状态机。
- 多 AI 协调已有回合黑板和部分硬守卫，但还需要继续扩展到报警、林越介入、假警察核验、隐藏证据等更多高风险场景。

### 叙事层面

- 叙事 AI 已接入行动叙事和环境叙事，但风格稳定性仍依赖 prompt 和导演评分器。
- fallback 叙事能保证可玩，但文学表现力有限。
- 叙事与线索展示之间还可以更紧密，避免玩家不知道哪些文本是有效信息。
- 导演评分器目前主要用于发现和重写叙事问题，尚未形成完整的可视化调试台和回合复盘报告。

### 技术层面

- 尚未接入数据库，缺少持久化存档、路线记录和 AI 决策日志。
- `.env` 为本地配置文件，不能提交真实 key；需要通过 `.env.example` 维护示例。
- 测试覆盖不足，规则系统和 AI 输出校验需要更多自动化测试。
- 前端 `App.tsx` 中仍保留部分 mock confirmation 逻辑，需要清理或接入真实确认流程。
- 当前 health 只粗略显示 provider 是否有 key，没有完整验证模型调用可用性。
- 项目中部分设计文档提到 SQLite，但当前还未实际接入。

## 11. 手工验证路线

可以用以下路线测试当前 MVP：

1. 输入：

```txt
我先不拆包裹，拍照发给林越，然后把椅子抵住门。
```

检查：时间推进、线索增加、林越状态变化、门防御状态变化。

2. 输入：

```txt
门外说自己是警察，我直接开门。
```

检查：是否触发高风险或死亡。

3. 尝试更稳妥路线：

```txt
我不开门，打开录音，要求对方报单位和警号，然后拨打 110 回拨核实。
```

检查：是否增加警察核验、录音等线索，并降低假警察风险。

4. 尝试证据生还路线：

```txt
我把包裹拍照备份到云端，发给林越，让他在楼下报警，不要上楼，然后锁窗拉帘并用行李箱堵门。
```

检查：是否更容易进入带证据生还或高分路线。

## 12. 项目定位总结

《murder-loop-ai》不是传统图形化逃脱游戏，也不是单 AI 聊天续写工具。它的核心体验是：

- 玩家用语言行动；
- 规则系统决定事实；
- 凶手 AI 在有限信息下反制；
- 叙事 AI 把结果写成悬疑小说；
- 每次死亡都变成下一轮的线索；
- 最终目标不是简单活下来，而是在公平规则下理解真相、保存证据并反制凶手。

项目当前已经具备 MVP 闭环，接下来的重点是扩大规则覆盖面、强化凶手对抗、完善证据链与回溯记忆，并将前端体验从原型打磨成完整可玩的悬疑互动小说 Demo。
