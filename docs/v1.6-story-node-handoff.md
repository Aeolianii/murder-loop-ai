## 项目背景

项目：`murder-loop-ai`

当前核心循环：

```text
玩家输入
-> ParserAgent 解析行动
-> RuleAgent / applyPlayerActions 执行规则
-> KillerAgent 选择反制
-> KillerResult
-> NarratorAgent 生成叙事
-> DirectorAgent 异步审查

```

本次目标：接入 v1.6 剧情节点。

核心原则：


```text

直接返回固定剧情文本 + 新线索 + 状态变化 + 推荐行动
```

## StoryNode 返回结构建议

```ts
export interface StoryNodeRecommendedAction {
  id: string;
  label: string;
  rationale: string;
  intent?: ActionPlan['intent'];
  target?: ActionPlan['target'];
}

export interface StoryNodeResolution {
  nodeId: string;
  title: string;
  text: string;
  tone: RuleResult['tone'];
  addedClueIds: string[];
  recommendedActions: StoryNodeRecommendedAction[];
  timePassed: number;
  threatDelta: number;
  stressDelta?: number;
  phase?: GameState['phase'];
}
```

推荐行动设计原则：

```text
推荐行动是玩家视角的下一步建议，不是系统替玩家行动。
推荐行动只能基于当前已发现的信息，不能泄露幕后真相。
每个 story node 建议返回 1-3 条推荐行动。
推荐行动优先鼓励安全、留证、核验、沟通和协作报警。
推荐行动可以映射到 ActionPlan 的 intent / target，方便前端未来做快捷按钮。
```

命中后建议伪装成正常 `TurnResolution`：

```text
playerResult = storyNode result
killerStrategy = skipped / retreat fallback
killerResult = empty system result
narration = storyNode text
actionNarration = storyNode text
ambientNarration = empty
recommendedActions = storyNode.recommendedActions
finalState = updatedState
```

前端建议兼容式新增：如果暂时不展示 `recommendedActions`，旧流程仍可只显示剧情文本；如果展示，则作为“下一步建议”区域单独呈现，不混入叙事正文。

## 林越线设计修订

林越不是知情人，也不是幕后线索持有者。

他的真实定位：

```text
林越看到包裹后觉得异常，判断女主可能正处在危险里。
他撤回消息不是为了隐瞒真相，而是不想让女主恐慌。
如果女主不追问，他会误以为自己应该上楼解决问题，从而进入危险。
如果女主追问，他会坦白自己的怀疑，并有机会被女主劝住，转为协助报警和外围观察。
```

也就是说，林越线采用“误判的行动者 + 信息中继者”方案：

```text
撤回消息
-> 玩家追问
-> 林越坦白只是怀疑，并不是知道内幕
-> 玩家劝阻林越不要上楼
-> 林越协助报警、记录楼下异常、保留通话或聊天证据
-> 好结局条件更容易成立
```

反向分支：

```text
撤回消息
-> 玩家不追问
-> 林越独自上楼
-> 林越失联 / 遭遇危险 / 甚至死亡
-> 玩家失去外部协助，后续结局压力提高
```

建议复用或新增的 `linYuePhase` 状态：

```text
worried              已撤回消息，处于担心状态
confessed_suspicion  玩家追问后，林越坦白自己只是觉得包裹危险
warned_not_to_come   女主明确阻止林越上楼
assisting_police     林越留在安全位置，协助报警或记录楼下动静
going_upstairs       玩家未追问或未劝阻，林越准备上楼
in_danger            林越进入危险状态
dead                 林越死亡，仅用于坏结局或严重失败分支
```

如果实现时不想扩大状态机，至少保留：

```text
worried
assisting_police
going_upstairs
in_danger
dead
```

```text
9. 多节点同时满足时只触发最高优先级
10. handoff_failed_2347 在无防守/证据条件时不触发
11. 玩家追问林越撤回消息后，linYuePhase 可进入 confessed_suspicion
12. 玩家劝阻林越上楼并要求协助报警后，linYuePhase 可进入 assisting_police
13. 玩家长期不追问或鼓励林越上楼时，linYuePhase 可进入 going_upstairs / in_danger
14. linYuePhase === assisting_police 可作为 handoff_failed_2347 的短期证据/协助条件
15. 每个 story node 命中后都返回至少 1 条 recommendedActions
16. recommendedActions 不泄露未发现真相，只基于当前线索给出安全下一步
17. buildStoryNodeTurnResolution 会把 storyNode.recommendedActions 透传到 TurnResolution
18. battery_critical 的 recommendedActions 第一优先级是找充电器并充电
19. 玩家执行充电行动后，phoneBattery 会随回合或时间逐渐上涨
20. phoneBattery 耗尽后进入死亡结局或强制失败结局
```

## 设计注意事项

1. 每回合只触发一个 story node。
2. story node 命中后跳过 Killer/Narrator/Director。
3. 不要用 Agent 生成这些节点文本。
4. 不要重复添加线索。
5. 不要让 `handoff_failed_2347` 无条件救玩家。
6. `battery_critical` 复用已有线索，不新增重复线索。
7. 不要再使用旧 id `chen_probe`。
8. 节点文本要保持第一人称有限视角，不泄露幕后真相。
9. 线索 id 描述事实，不提前指认凶手。
10. 优先复用现有状态字段，不够再加字段。
11. 林越不是知情人，不要写成“他知道包裹内幕”或“他掌握关键秘密”。
12. 林越撤回消息的动机是担心女主害怕；他真正的风险来自误判后想独自上楼。
13. 好结局方向应奖励玩家追问、沟通和协作报警，而不是奖励玩家让林越冒险接近现场。
14. 林越协助时只能提供外围观察、聊天记录、报警补充和证据备份，不能直接替玩家揭露真相。
15. 推荐行动是 UI/系统提示，不是叙事正文；不要让它替玩家自动执行行动。
16. 推荐行动要鼓励玩家做“合理下一步”，但不能保证这是唯一正确答案。
17. 推荐行动不能提前暴露 killer 策略、未来节点或结局条件。
18. battery_critical 不是单纯省电提醒；它提示玩家必须主动接上房间内的充电器。
19. 充电后前端电量应逐渐上涨，不要一次性跳满，避免破坏资源压力。
20. 手机没电后会进入死亡结局或强制失败结局，因此低电量推荐行动优先级应高于继续拍摄、录音或等待。
